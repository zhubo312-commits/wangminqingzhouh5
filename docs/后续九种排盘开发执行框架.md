## 1. 文档用途

本文件是后续模型实现剩余九种排盘时的强制执行框架。它解决的是“怎样可靠地增加一种完整排盘”，不是让模型一次性生成九套相似页面。

每次任务只实现一种排盘，并按以下闭环推进：

`资料就绪 → 专业结构确认 → 数据契约 → 算法服务 → Fastify 接口与短期上下文 → 表单页 → 结果页 → 状态与恢复 → 三档移动端验收 → 合并`

九种排盘不得全部开发完成后再统一合并。正确方式是一个盘种完成、验收、合并后，下一个盘种再从最新 `main` 开始。

## 2. 给执行模型的总指令

执行任何一个盘种前，必须先阅读：

1. 本文件。
2. `docs/专业排盘统一设计规范.md`。
3. `docs/后续九种排盘推进清单.md`。
4. 已完成的生平子时与遁甲学代码、测试和功能设计文档。

必须遵守以下边界：

- 一次任务只做一个盘种，不能顺手开启其他盘种。
- 只有清单达到“可开发”状态的盘种才能进入编码。
- 算法来源、输入含义、输出字段或专业阅读顺序不明确时，停止编码并把缺口写入清单；不得猜测、拼凑或伪造盘面。
- 不把旧页面、接口字段顺序或原始 JSON 直接当成新版信息架构。
- 但必须先完整操作和盘点原始页面：起盘模式、全部字段与条件显隐、默认值、结果模块、详情层级、辅助工具和页面链路均须进入功能对照矩阵，不得在重构信息架构时静默丢失。
- 广告、关注、登录、付费、旧老师入口和旧视觉装饰可以按既定非目标排除；算法参数、起盘能力、盘面结构和结果工具只有在明确记录并确认后才允许移除。
- 不在前端重新实现排盘算法；浏览器只调用 Fastify，Fastify 再调用内网 Java 排盘服务。
- 不把姓名、时间、地区、问题或完整盘面放进 URL；结果恢复继续使用短期 `paipan_ref`。
- 当前只有生平子时允许展示智能老师入口。其他盘种除非另有明确需求，禁止添加老师入口、自动解读、吉凶结论或建议。
- 盘种未完成全部验收前，`catalog.ts` 中继续保持 `enabled: false`。
- 不改变首页对登录、聊天、报告和支付的既有边界。
- 不部署、不推送远端、不修改线上服务，除非用户在当前任务中另行明确授权。
- 不提交密钥、个人信息、真实用户盘面、SQLite 数据库、构建产物或本地环境文件。

## 4. 分支与合并策略

### 4.1 开始条件

开始一个盘种前先确认：

```bash
git status --short
git branch --show-current
```

要求：

- 从已验收的最新 `main` 开始。
- 工作区必须干净；发现不属于当前任务的修改时，不覆盖、不回退、不擅自提交。
- 分支建议命名为 `feat/paipan-<slug>`，例如 `feat/paipan-meihua`。

### 4.2 合并节奏

每个盘种使用短分支，完成后立即验收并合并。下一个盘种从合并后的最新 `main` 创建分支。

一个盘种建议拆成以下逻辑提交：

1. 功能设计、脱敏样例与黄金用例。
2. 数据契约、Java 算法接口和 Fastify 接口。
3. 表单页、结果页、状态恢复和路由。
4. 单元测试、E2E、预览图及清单更新。

提交数量可以因规模调整，但不能把九个盘种混在同一个提交或分支中。

### 4.3 并行限制

公共底座尚未稳定前不得并行开发九个盘种。底座稳定后最多并行两至三个真正独立的盘种，并满足：

- 公共契约入口、`App.tsx`、`catalog.ts`、公共 CSS、上下文存储和 OpenAPI 由一个集成负责人维护。
- 各盘种分支主要新增自己的目录、契约模块、测试夹具和功能设计文档。
- 任何公共抽象都先在一个盘种中验证，再提供给其他分支；不得让多个分支同时发明不同版本。

## 5. P0：第三个盘种前的公共底座

在开发第一个新增盘种前，先完成一次独立的公共底座任务。该任务只做可由现有两个盘种证明的抽象，不能提前设计一个覆盖所有术数的万能组件。

### 5.1 应优先抽离

建议在 `apps/web/src/features/paipan/shared/` 建立稳定公共层：

- `PaipanPageShell`：宣纸背景、最大宽度、安全区和统一头部骨架。
- `PaipanSectionCard`：编号、标题、卡片与模块间距。
- `InfoGrid` / `InfoPair`：信息摘要与两列信息。
- `InlineSelectionGrid`：平铺选择、可收起行内详情和指向气泡。
- `PaipanEmptyState`：加载、失效、错误和重试。
- `FiveElementLabel`：确有五行数据的盘种复用。
- `ChartTable`：只有在第二种盘面也能复用时再抽离，不能为了抽象而压平不同盘体。

继续复用现有 `PageHeader`、`MobileWheelPicker` 和 `InterpretationEntry`。智能老师入口仍只在生平子时使用。

### 5.2 上下文存储扩展

对以下文件先做最小、可测试的扩展设计：

- `apps/server/src/paipan/paipan-context.repository.ts`
- `apps/server/src/paipan/paipan-context.service.ts`
- `apps/server/src/paipan/paipan-context.service.test.ts`
- `packages/contracts/src/index.ts` 或其后续拆分模块

目标：

- 存储层保存统一的版本化信封：`chartType`、`schemaVersion`、`chartRequest`、`chart`、`generatedAt`、`expiresAt`。
- 各盘种在解析时继续使用自己的 Zod 请求与响应 Schema，不能用 `unknown` 绕过运行时校验。
- 保持现有生平子时、遁甲学响应结构、错误语义和 `paipan_ref` 行为不变。
- 新增盘种不需要继续复制 `createXxx`、`resolveXxx` 和仓储分支判断；具体实现可以使用类型安全的注册表或等价的最小方案。
- 新增回归测试证明旧的两个盘种仍能创建、恢复、过期和拒绝错误盘型。

### 5.3 样式边界

- 全局文件只保留设计令牌和确实公共的组件样式。
- 单盘样式使用盘种前缀或局部文件，禁止覆盖全局字号、圆角、模块间距和主题变量。
- 不通过 `overflow-x: hidden` 掩盖真实布局溢出；E2E 必须验证 `scrollWidth <= clientWidth`。
- 不新增无必要动效。所有动效尊重 `prefers-reduced-motion`，只使用 `transform`、`opacity` 等低成本属性。

P0 完成后必须单独跑完整回归并形成独立提交，再开始第一个新增盘种。

## 6. 单盘纵向开发流程

### 阶段 A：资料与专业结构

先完成该盘种的 Definition of Ready：

1. 确认用户可见名称、内部算法名称、`slug`、路由和 `chartType`，不能只凭“逻辑学”“星像学”等展示名称猜算法。
2. 定位经过授权的算法来源、仓库、文件或接口，并记录版本或提交号。
3. 固化原始页面和子页面地址、版本化脚本、采集时间与 SHA-256，保存关键页面截图。
4. 实际操作全部起盘方式、条件组合与结果工具，形成原始功能清单和功能对照矩阵。
5. 为每种起盘模式准备至少一份脱敏请求、原始响应和可信黄金结果。
6. 列出合法输入、默认值、互斥关系、条件显隐、时间/历法/地区/方位规则和错误边界。
7. 逐字段说明输出含义，区分核心盘体、核验信息、研读关系、辅助信息和算法中间数据。
8. 由专业视角写出正常阅读顺序，并确定“始终可见、默认展开、按需展开、不直接展示”。
9. 说明模块为什么合并或拆分，并逐项标明原始功能是原样保留、等价重构、经确认移除还是阻塞。

资料不足时，只更新清单和功能设计草案，不进入编码。

### 阶段 B：功能设计文档

新增 `docs/<盘种>页面功能设计.md`，至少包含：

- 定位、算法依据及非目标。
- 原始页面版本证据、功能清单和新旧功能对照矩阵。
- 表单输入、默认值、校验和异常情况。
- 专业阅读路径。
- 结果页模块顺序与显示层级。
- 模块合并/拆分理由。
- 请求、响应、`chartType` 与 `schemaVersion`。
- 加载、空态、错误、过期、刷新恢复和返回链路。
- 360/390/430px 的局部例外与处理方式。
- 黄金用例、测试范围和验收标准。

功能对照矩阵不得留空。任何“经确认移除”项都要写明它属于广告、关注、登录、付费、旧解读或其他非目标，并记录确认依据；任何“阻塞”项都必须让入口保持关闭。

功能设计未确认前，不先画漂亮页面再倒推数据。

### 阶段 C：共享契约与 OpenAPI

为盘种建立独立、明确的请求与响应 Schema：

- TypeScript/Zod 契约放入 `packages/contracts`，必要时按盘种拆文件并从入口统一导出。
- 公开契约同步到 `openapi.yaml`。
- URL 使用稳定的 kebab-case；`chartType` 使用稳定的 snake_case；版本建议为 `guoxue.paipan.<slug>.v1`。
- 请求字段严格校验日期、枚举、范围和互斥条件，不能把全部字段设成可选后交给算法猜。
- 响应只暴露产品需要的稳定数据，不暴露 Java 类名、调试字段或无用途的算法中间值。
- 排盘响应包含短期 `paipan_ref` 与过期时间；上下文恢复返回版本化请求和完整盘面。

契约必须先于 UI 固定，前后端不得各维护一套同名但不同义的字段。

### 阶段 D：Java 算法服务

实现或接入路径应保持：

`Controller → 请求校验/转换 → Engine → 已授权算法实现 → 稳定响应模型`

要求：

- 优先复用已授权且经过黄金结果核验的算法，不重写成熟算法。
- 为盘种建立独立 Controller、Models 和 Engine 边界。
- 内部接口位于 `/internal/v1/<slug>/...`，不由浏览器直接访问。
- 对非法日期、历法冲突、地区缺失、无候选结果、算法异常等返回明确错误，不回传堆栈。
- 至少提供 Engine 黄金用例测试与 Controller 契约/错误测试。
- 不因测试难写而跳过运行时校验。

### 阶段 E：Fastify 接口与短期上下文

涉及文件通常包括：

- `apps/server/src/paipan/paipan-client.ts`
- `apps/server/src/paipan/paipan.routes.ts`
- `apps/server/src/paipan/paipan-context.service.ts`
- `apps/server/src/paipan/paipan-context.repository.ts`
- 相应测试与脱敏 fixture

要求：

- Fastify 使用共享 Zod Schema 校验浏览器请求和 Java 响应。
- 只由 Fastify 调用 Java 内部接口。
- 生成高熵 `paipan_ref`，数据库只保存引用哈希。
- 上下文按 TTL 过期，404 与 410 等现有错误语义保持一致。
- 盘种不匹配或 Schema 版本不匹配时拒绝恢复，不能把一种盘解析成另一种盘。
- 对 Java 不可用、超时、错误响应和无效 JSON 提供结构化错误及测试。

### 阶段 F：前端表单、结果与状态

每个盘种在 `apps/web/src/features/paipan/<slug>/` 下独立组织，建议包含：

- `<Name>Session.tsx`
- `<Name>FormPage.tsx`
- `<Name>ResultPage.tsx`
- 盘种局部常量、类型或小组件
- 对应单元测试

要求：

- 路由保持“导航 → 表单 → 结果”，结果返回表单，表单返回专业排盘导航。
- 表单只收集算法确实需要的输入；日期与时间分开选择，移动端优先使用现有滚轮组件。
- 原始页面提供的全部起盘模式、算法字段、选项、默认行为和条件显隐均须保留；允许重新分组，不允许只实现默认路径。
- 提交时禁用重复操作，并提供加载、字段错误、接口错误和重试反馈。
- 当前标签页仅在 `sessionStorage` 保存 `paipan_ref`，不保存完整盘面。
- 结果刷新通过上下文接口恢复；过期或不存在时提供重新排盘入口。
- 结果模块按专业阅读路径组织，不照抄原始 JSON。
- 原始页面已有的结果模块、详情层级、上一/下一、切换、联动、展开、放大和重排等工具必须原样保留或等价重构。
- 核心盘体优先保证 360px 可读，确实无法压缩的局部盘面才允许自身横向滚动，整页不得横向溢出。
- 触控目标不小于 44×44px，动态展开使用正确的 `aria-expanded`、`aria-pressed` 和必要的 `aria-live`。
- 不使用占位图片、外部随机图片、emoji 或虚构文案。

### 阶段 G：路由与导航开放

只有前述链路和测试完成后，才修改：

- `apps/web/src/App.tsx`
- `apps/web/src/features/paipan/catalog.ts`

开放时确认：

- 路由、返回链路和直接刷新均正常。
- `enabled: true` 与有效 `path` 同时提交。
- 未完成盘种仍显示“即将上线”，不能误开。

## 7. 测试与视觉验收

### 7.1 必须覆盖

- 共享契约：合法、边界和非法请求。
- Java Engine：黄金结果及关键边界。
- Java Controller：请求、响应和错误映射。
- Fastify Client/Route：正常、上游不可用、超时、无效响应。
- 上下文：创建、恢复、过期、未找到、盘种不匹配、版本不匹配。
- 前端：表单模式、校验、提交、结果模块、错误、重试、返回和刷新恢复。
- E2E：360、390、430 三档宽度，全链路和无整页横向溢出。
- 视觉：长名称、长地区、大字号、安全区、表格四角、选择详情和收起状态。

### 7.2 完整验证命令

在仓库根目录依次执行：

```bash
git diff --check
npm run typecheck
npm test
npm run build
npm run test:e2e
```

随后在 Java 服务目录执行：

```bash
cd services/paipan
mvn verify
```

还需要为该盘种生成并人工检查：

- 360px 表单与结果图。
- 390px 表单与结果图。
- 430px 表单与结果图。

测试失败、截图未检查或只有局部用例通过时，状态只能写“部分完成”，不能写“已完成”。

## 8. 单盘 Definition of Done

只有以下条件全部满足，清单状态才能改为“已验收”：

- [ ] 算法来源、版本和授权边界已记录。

- [ ] 功能设计文档完整，专业阅读路径已确认。
- [ ] 原始页面证据、功能清单和新旧功能对照矩阵完整，所有移除项均有确认依据。
- [ ] Zod 契约和 OpenAPI 同步。
- [ ] Java Engine、Controller 和测试完成。
- [ ] Fastify Client、Route、上下文创建/恢复和测试完成。
- [ ] 前端表单、结果、加载、错误、过期和刷新恢复完成。
- [ ] 全部原始起盘模式、条件显隐、结果模块和结果工具均已通过功能对照验收。
- [ ] 只有该盘种的导航项被正确开放。
- [ ] Node typecheck/test/build 全部通过。
- [ ] Java `mvn verify` 通过。
- [ ] 360/390/430 三档 E2E 全部通过。

## 10. 可直接交给下一模型的任务模板

```text
请在 /Users/zhubo/开发文件/轻舟发现页 仓库中，按照以下文件执行下一种排盘：

1. docs/后续九种排盘开发执行框架.md
2. docs/专业排盘统一设计规范.md
```
